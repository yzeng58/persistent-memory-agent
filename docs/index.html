Personal AI Is a Memory Architecture Problem

Most of the problems I encountered with general-purpose assistants looked unrelated: they forgot facts about me, failed to maintain what they wrote, surfaced irrelevant context, kept facts that were no longer true, and gave generic advice. But all five came down to the same issue: what the system stores and how a task reaches it. I found that they can be addressed by a carefully designed memory system that satisfies two criteria: (1) every piece of information or behavior has one canonical place; and (2) every task that needs it has a written path to that place. I built such a system and now use it across work and daily life. The remaining problem is architectural. A model can follow a structure once it exists, but it still cannot decide reliably when to reuse, split, move, or create components. The next step is to train models to make those decisions themselves.

01

Why I built my own personal assistant

I use Codex, Claude Code, and Copilot CLI every day. Each of them will hold on to a rough picture of who I am. Without a carefully designed harness, none of them keeps the rules and the details across the many different things I need help with. That is what stops them from being a real personal assistant. A real one, in my view, should be in charge of everything about me.

1.1 It does not know me

It is worth starting with what the phrase means. Booking a flight? Sending an email? By that description, plenty of assistants already qualify. But do you actually use Codex, Claude Code, or Copilot CLI to book a flight or send an email?

No.

Scenario 1. Booking a flight

I ask it to book a flight. To do that it needs to know which cards I hold and which one to pay with, which airline I collect miles on, and what I am optimising for. It knows none of that, so it comes back with flights I would not have picked, and I go and book it myself.

Scenario 2. Sending an email

I ask it to email someone. It does not know which of my accounts to send from, and I keep several for different purposes. It cannot find the recipient’s address without being told. The draft comes back in the wrong register, so I specify the tone as well. By the time I have specified all of it, I have written the email.

Both times the work came back to me, and for the same reason. Nothing it needed was written down anywhere it could reach.

What I set out to build is an assistant that is close to a human one. Getting from an agent that knows nothing about you to one that can decide and act on your behalf takes more than one fix. Part of it is easy enough to picture: a decision path, written down as harness, for each kind of task it has to handle. The hard part is memory.

1.2 It does not maintain what it writes

Now take a task that would take a person months rather than an afternoon. Over that length, most of the work is not writing new code. It is staying consistent with the code that is already there. That is the part it does not do. A program that should have been a thousand lines comes back as fifty thousand, because every step writes its own version of what the step before it already had.

I run into this whenever I write a paper.

Scenario 3. The second experiment

I write down the experiment design and ask it to implement the code. The first experiment comes out fine. The second one is supposed to run the same evaluation. Instead of calling what is already there, it writes its own, and some detail never lines up with the first. The two sets of numbers then cannot go in the same table.

A person would write the evaluation once and call it from every experiment after that. An agent does not, unless it is told, and it has to be told every time.

The same thing happens when I ask it to save something for later.

Scenario 4. Saving a project idea

While working on a project, I find an idea that will matter later and ask the agent to save it. It creates idea.md in the project and writes the idea there. But it does not add a pointer from the project instructions to the new file. The file is on disk, but the agent never reads it again. It saved the idea without maintaining the path that would make the idea useful later.

After a few rounds of this, the project fills with files that exist but are never read.

In both cases, what it wrote was fine on its own. What it failed to maintain was the project around it.

1.3 It brings up what I did not ask about

You have probably seen this one too.

Scenario 5. An air fryer for my parents

I ask it which air fryer to buy. It comes back with the small ones, because I live in an apartment and I told it once that my counter space is tight. That is true, and it is not the point. The air fryer is for my parents, and their kitchen is nothing like mine. The ones I would have picked are already off the list, ruled out for the wrong kitchen.

Nothing it says here is false, which is what makes it awkward to push back on. What comes back is true and it is simply not what I asked about. Most of the time this is noise and I read past it.

1.4 It holds on to what is no longer true

Sometimes the thing it brings back is not just beside the point. It stopped being true a while ago.

Scenario 6. A deadline that passed months ago

One week I was up against a deadline and I told it so. That went into memory. Months later the deadline is long gone, and it is still answering as though I am short on time. Cut the scope, ship something that works for now, leave the rest. I never told it the deadline had passed, because it never occurred to me that I would have to.

Saving something takes one sentence. Taking it back takes me noticing that it is still in there, which is the part I never do. So the answer gets built on top of it, and I have to catch the old fact before I can use any of what it said.

These two are the first gap seen from the other side. Nothing decides what belongs to the question being asked, so the thing I need can be missing and the thing I do not need can arrive, in the same answer.

1.5 It answers like anyone else

The gaps above are all about what it holds on to and where. This one points the other way. Sometimes I want an answer I could not have taught it, because I do not have it myself. What I get instead is the answer of a median person. When I bring it a career question while I am upset, it tells me it will be fine. That is not what I want to hear. I want it to answer like someone who knows the field.

Negotiation is the clearest case.

Scenario 7. Pushing back on a rent increase

I ask how to push back on a rent increase. What I get is the advice anyone would give: be polite, explain the situation, ask whether there is any flexibility. It has no read on the person on the other side. What they are worried about, what a specific number does to the conversation once it has been said out loud, when saying nothing is worth more than another sentence of justification.

That is the part that decides how it goes, and it is not what the average answer contains.

02

Organized memory is all you need

Most of what went wrong above went away once I restructured the whole memory system, with AI doing the restructuring. The design came from one specific problem, so I will start there.

I have a skill for writing papers. Part of it is a list of rules for making figures: how big the fonts have to be, which colours still work when the paper is printed in black and white, what to do when the legend does not fit. I built that list slowly, by fixing figures that had come out badly. Later I added a skill for writing blog posts, which also needs figures. The assistant did not use the list I already had. It worked out its own figure rules from scratch and wrote them into the new skill. The two lists said roughly the same things, so I left them alone. A few months later one of my paper figures came out unreadable, and I added a new rule to the list in the paper skill. The next blog post had the same unreadable figure. The blog skill was reading its own list, and that list had never been updated. I had already solved this problem once, and I had to solve it again.

Nothing was lost or forgotten here. Both lists were sitting on disk, and each skill read the right one. The problem is that the same rules were stored in two places, so fixing one place could never fix both.

Fixing it properly takes two steps. First, the figure rules come out of both skills and go into one file, so only one copy is left. Second, both skills have to point at that file, otherwise nobody opens it. Both steps are needed. If I only do the first, I end up with a file that no skill mentions, so it never gets read. If I only do the second, the two skills point at two separate copies, and the copies still go out of sync.

Those two steps are not specific to figures. They are the two rules the whole memory system runs on. As long as both hold, anything new I put into the system actually gets used, and the failures from the last section stop happening.

  1. One path per piece of information. Every piece of information can be found in exactly one place. Not two places, and not “probably somewhere”.
  2. A path that leads there. When a task needs that information, the harness routes to the file that holds it, so the model actually opens it. Without this, a file can sit on disk and never be read, because no instruction and no skill ever names it.

I go back through those failures one at a time below. Someone still has to design the layout. Models cannot do that part yet, so I decided the structure myself and had the assistant fill it in. What that limits is who can build such a system today, not whether it works once built. I come back to it at the end.

2.1 Sending one email

In the last section the assistant could not send an email for me. It did not have the address, and the draft it wrote sounded like a message to a stranger. Here is how that same request runs now.

Four separate things are needed, and each one is stored in exactly one place. Who the person is, how I know them, and what their address is: one folder per person, under network/. Which of my four accounts to send from: one decision table, inside email-ops. How I write to a collaborator as opposed to someone I have never met: one writing guide, also inside email-ops. The login for each account: one encrypted file, reached through account-ops.

None of these are copied anywhere else. The folder for a person says nothing about tone. email-ops does not store a single email address. When a collaborator moves to a new job, I change one line in one folder, and every email after that is correct.

That is the first rule doing its work. The second rule is what makes any of these files get opened.

When I say email my collaborator about the paper draft, the assistant does not go searching through the file tree. The top-level instruction file has a routing table, and two lines in it apply here. Anything involving email goes to email-ops. Anything that mentions a person goes to people-ops, which opens the lookup table in network/ and from there the folder for that person. email-ops then names the two files it needs, the account table and the writing guide. Each file names the next one.

By the time there is a draft, the assistant has opened the person’s folder, the account table, and the writing guide, in that order. It did not search for any of them. Each one was named by the step before it.

2.2 Booking a flight

A flight needs more than one kind of fact, and they belong to completely different parts of my life. Which airport I fly out of. Which card earns what on airfare. My frequent flyer numbers. My passport number. Whether anyone is travelling with me. Every one of those has exactly one home, and none of those homes is inside the travel module.

travel-ops holds how to book a flight: how to compare points against cash, when a nearby airport is worth the drive, what to check before paying. It stores no passport number, no card number, and no airline account. Those sit in the identity, finance, and credential stores, where everything else that needs them also looks.

The preferences file does the joining. It carries a small table that says, for each kind of travel fact, which file owns it. The assistant does not guess where a passport number might be. It reads the row.

When the booking is done, the result goes back to one place: a folder for that trip, holding the reservation number, the seats, the total, and which card paid. My calendar entry is generated from that folder. If the flight changes, I change the folder, and the calendar entry follows. The calendar never becomes a second version of the truth.

2.3 The second experiment

This one is not about finding a fact. Nothing was missing when the assistant rewrote my evaluation. It just did not look for what was already there.

So the rule is written into the experiment procedure itself: before writing any measurement, search the project for one that already exists, and if it exists, call it. That check is a step in the module, not a preference I have to state each time.

If nothing is found, the evaluation gets written once, in a file whose job is to hold it. The next experiment finds it and calls it. That is the same shape as the figure rules: the second copy is what causes the damage, so the procedure stops the second copy from being created at all.

2.4 Saving an idea

Earlier, the assistant saved an idea to a file and then never read that file again. The file was real. The problem was that nothing pointed at it, so no later task had a reason to open it.

Now only one module is allowed to create, move, or delete anything in the system. When it saves something, it consults the storage tree for where that kind of thing goes, so the location is decided by a rule rather than by whatever folder happens to be open. Then it writes the pointer.

The pointer is not optional, and it is not a separate task I might forget. Saving means both: the file, and a line somewhere that names it. A file with no pointer is exactly the failure from the last section, and it is the same thing that would happen if I moved the figure rules into their own file and stopped there.

2.5 An air fryer for my parents

The air fryer answer went wrong because a true fact about my kitchen was applied to somebody else’s kitchen. So the question is what decides that a fact about my apartment is not relevant here.

The storage tree answers it. Information is filed by who or what it is about, not by which task might use it. My counter space is a fact about my apartment, so it lives with the apartment. My parents’ kitchen is a fact about my parents, so it lives in their folder.

When the purchase is for my parents, the chain runs through their folder. Nothing in that chain names the apartment file, so the apartment file is never opened. It is not retrieved and then discarded, and it is not outranked by something more relevant. There is simply no path to it from this question.

That is the second rule read backwards. A path that leads to the right file is also, by construction, a path that does not lead anywhere else. Relevance stops being a scoring problem and becomes a question of which files this task is allowed to reach.

2.6 A deadline that passed

The stale deadline is different again. It was filed correctly and retrieved correctly. It had just stopped being true, and nothing in the system was watching for that.

The fix is to sort things by how long they stay true before deciding where to put them.

Some facts stay true until I change them: where I live, which cards I hold, how I like figures to look. Those go into the personal record, and because each one sits in exactly one file, I change it in one place when it changes. That is the whole update story. There is no second copy left behind to contradict the first.

Other facts have an end date built in. A deadline is one of those. It does not go into the personal record at all. It goes into the reminder file, where every entry carries the date it becomes relevant and a status. Once the date passes, it stops being shown. I do not have to remember to take it back, which is the part I was never going to do.

The third case is the one that surprised me. Some facts are not mine to hold. My immigration entry record and my account balances are true right up until someone else changes them, and nobody tells me when they do. Storing those is worse than not storing them, because a stored copy looks current and is not. So the system stores the address of the source instead of the value, and fetches it at the moment it is needed.

2.7 Pushing back on a rent increase

The last gap is not a memory problem. When I asked how to push back on a rent increase, nothing about me was missing. What was missing was a way of answering that question that is better than the average one.

So that had to be written down too. Not facts about me this time, but a way of working through a negotiation.

The negotiation module holds a four-phase sequence: work out my walk-away position and what the other side is worried about, open without anchoring myself, ask questions that surface what they actually need, and only then put a number on the table. Below it sit the three books the sequence is drawn from, so a specific move can be looked up rather than paraphrased from memory.

The last step is the one that changes the output most. Before I see a draft, it is checked against a list of moves that read as weak: apologising for asking, justifying a number before it has been questioned, offering a compromise nobody requested. If the draft contains any of them, it gets rewritten. Only what survives that check reaches me.

This is where the two rules earn something beyond consistency. Everything I have learned about negotiating lives in one place, so improving it improves every negotiation after that, and the route into it is written down, so I get it without having to remember that I own it.

What the system looks like now

This is what the system looks like after being used across many parts of my life. The first half shows the personal information it maintains. The second shows the work it can do with that information.

3.1 What it knows about me

Nine areas hold personal information that should last. I do not show the contents, only what each area is for and how many files it contains.

Area Files What it holds
living/ 614 apartment, floor plans, car, furniture inventory, subscriptions
network/ 49 one folder per person, with a lookup table at the top; work, friends, family
health/ 13 one folder per test type, reports named by year, summary at the top
identity_documents/ 13 passport, visa, work authorization, student records
career/ 9 employment documents, CV, equity statements, long-range career planning
finance/ 9 one folder per institution; card and account numbers in an encrypted file
aesthetic-care/ 4 service providers: who, where, what was done, what it cost
travel/ 4 stable preferences, a reusable packing baseline, one folder per trip
education/ 3 degree certificates, with only one copy in the system

The areas are very different in size. living/ is about one hundred times larger than education/. That is fine because the folders give information an address; they are not meant to be equal in size. Four flat files, academic.md, career.md, identity.md, and side-business.md, existed before the directory layout. They still sit next to the directories. Two have the same name as a directory, which creates an ambiguity I have not resolved yet.

The system has 72 modules, each responsible for one kind of task. I list 70 below. I hide two because their names reveal private information. Four names marked with ∗ replace internal tool names with general names.

  • sync-all: pushes every tracked project to its remote repository.
  • clean-copilot: runs agent experiments in an isolated container with selected configuration.
  • reporting-ops: runs the daily briefing and weekly review that can trigger system changes.

Communication and people

  • apple-notification: sends urgent alerts to a phone and watch.
  • people-ops: writes to the network/ area, with one folder for each person.
  • workplace-communication: helps with difficult work conversations and replies.

  • social-scout: collects opinions from online communities when real experiences matter.

Research and writing

  • paper-ops: handles outlines, drafts, figures, rebuttals, and final versions.

Compute and experiments

  • experiment-ops: designs, submits, evaluates, and reports experiments.
  • code-writing: the only module that controls code changes, code placement, and function contracts.
  • gpu-cluster-ops∗, chtc-ops: manage two clusters with different schedulers and queue rules.
  • job-scheduler-cli∗: submits jobs, reads logs, and downloads results.
  • azure-ops: stores artifacts that are too large for experiment tracking.
  • wandb-ops: finds experiment runs and downloads results.

Money

  • asset-snapshot: reads live balances and never estimates or rounds them.
  • investment-ops: handles reviews, contributions, vesting, and stock screening.

Life administration

  • calendar-ops: reads a local snapshot of four calendars before any API call and writes to one calendar.
  • travel-ops: handles flights, points, packing lists, and reservations.
  • address-change-ops: lists and completes every update required after a move.
  • apartment-search: compares rent after adding fees that advertisements leave out.

  • account-ops: stores credentials and runs before any login.

  • secondhand-ops, facebook-ops: manage resale listings and buyer messages.

Personal

Public presence

04

Future directions

The system can follow an architecture once a person has designed it. It cannot yet design that architecture reliably. Each new fact, rule, or piece of code creates a structural choice: add it to an existing file, create a new file, split a branch, reuse an abstraction, or move ownership somewhere else. I call the capability needed to make those choices architectural reasoning: placing a local change inside a global structure while preserving one owner for each piece, the paths that reach it, and the dependencies that already rely on it. Address-space induction is the memory-specific form of the same capability.

The next question is whether a model can learn to make these decisions on its own. Training can start with an existing system and one new requirement, such as a feature to implement or a new kind of information to store. The model has to decide what to reuse, what to split, and where the new code or information belongs, then update any routes and callers affected by that choice. The result can be judged by the same two rules from Section 2: each piece of information or behavior has one place, and every task that needs it has a path to that place. The goal is to make those two rules hold not just after one change, but across a long sequence of them.
