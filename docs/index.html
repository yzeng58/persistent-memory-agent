How to make a personal AI system that knows you well

01

Where it fell short

I did not plan to build a system. I built it because the same problems kept coming back. For about a year, I used a general-purpose assistant every day for work, money, health, and immigration paperwork. The model was often smart enough to answer well. The problems came from the system around the model: how it found information, chose an approach, and saved new lessons. I could change all three without changing the model itself.

1.1 It remembers the wrong things

I saw two opposite problems:

  • It brought up old facts that did not matter. Some details were true but unrelated to my question. They then pulled the answer in the wrong direction.
  • It left out the fact that should control the answer. It missed a hard constraint that should have changed the answer. It also gave no sign that it had searched for that constraint and failed to find it.

The two problems often appeared in the same answer. Neither came with a warning. A fixed-size retrieval step can create this pattern. If the important fact does not rank high enough, the system leaves it out and fills the available slots with other facts. This does not prove that any product works this way. It only describes the pattern I needed my own system to prevent.

I did not need to know how a vendor built its product. I needed to build a system where this failure could not happen. Similarity retrieval has three limits that matter here. Better tuning does not remove them.

  • The system does not give a fact one stable key across updates. A vector store can give each record an ID and overwrite a record with the same ID. But it does not know that “I moved to B” should replace “I live at A.” Without another rule, both records stay in the store. At read time, the record closer to the query wins. You can add recency to the ranking, but that is still a ranking rule. It is not a true update of one value.
  • Similarity does not show which fact is a rule. “This position is locked and cannot be sold” and “I like this stock” may be close in embedding space. But the first sentence is a hard rule, while the second is only a preference. Similarity does not tell the system which fact must control the answer.
  • A text collection does not store current state. Retrieval finds text about a topic. A personal assistant often needs the current value of something: where I live, what I owe, or which document I filed. These questions have exact answers. An approximate answer is still a wrong answer.

The assistant did not need more facts about me. It needed a way to decide which facts controlled the answer.

1.2 It answers like the median person

I would ask for help with a workplace problem and receive emotional support. The response was not always bad, but it was often not what I needed. The model already knew about negotiation, organisational behaviour, and difficult messages. The system had no step that chose which area of knowledge to use.

I do not think this is a model defect. A model learns from what many people write and what many people rate highly. It will often give the answer that works for the average person. Many people who say “my manager did X and I feel Y” want comfort. I may want a negotiation plan instead. The default can be reasonable for most users and still be wrong for me.

This is separate from 1.1:

  • Problem 1.1 is a fact-selection problem. The system had the right information but did not select it.
  • Problem 1.2 is an expertise-selection problem. The system had the right knowledge but chose the wrong field or method.

More personal context does not fix 1.2. Even with a perfect profile, the assistant can still give the average answer with more personal details. The system must choose an approach before it writes the answer. It also needs a set of clear approaches to choose from.

1.3 It never gets better

My corrections did not last. I could explain a preference, point out a repeated mistake, or find a better process. A few weeks later, the assistant would make the same mistake again.

Two separate problems caused this:

  • The system did not start reflection by itself. The system never stopped to ask, “What should change after this task?” It reflected only when I asked. That happened rarely, and only after I noticed the problem myself.
  • The system had no clear place to save a lesson. A lesson saved in one large memory pool is useful only if a later query retrieves it. That returns us to the problem in 1.1. Saving text is not the same as learning. If the system cannot make sure it reads the lesson later, the lesson has not changed its behaviour.

A deeper problem took me longer to see: the system usually needs to change a procedure, not save a fact. “Check the account balance before proposing a purchase” is not a memory. It is a checklist step. If the checklist does not exist, there is no clear place to add the lesson. The system can only save a note and hope it finds that note later.

02

Approach

I use one fix for each problem. The order matters. Section 2.2 depends on 2.1, and section 2.3 depends on both.

2.1 Address space and assignment rules

The main rule is simple: every fact that should last has one path. The fact itself decides the path, not the question used to find it.

By maintainability I mean two invariants:

  • Every stored fact must exist in one place. A fact cannot be “probably saved somewhere.” It must have one file in one location that I can check.
  • The system must know where to look. Otherwise, I cannot verify the first rule. I can confirm that a fact exists only if I know every place where it could be.

One tree, walked twice

The file that defines the address space opens with two lines, which define the whole design: 

Walk this tree before storing a file.
Walk the same tree when looking for one.

Storing and finding use the same path through the tree. Suppose I save the fact, “this position is locked and cannot be sold.” The fact is about my money, so the tree sends it to finance/. Months later, I ask whether I can sell. The question is also about my money, so the tree sends me to the same file. I do not need to remember the original wording. The tree uses the subject of the fact, not the words in the sentence.

Similarity retrieval works differently. When the system writes, it embeds the fact. When it reads, it embeds the question. The two texts are different: 

write:  embed("locked, cannot be sold") → insert
read:   embed("can I sell this?")       → top-k

These are two separate functions. One does not reverse the other. Nothing guarantees that the question will find the place where the fact was stored. A saved fact can still be impossible to reach.

An empty tree lookup has only two possible causes. Either the fact was never saved, or the tree changed after the fact was saved. I can check the first case with ls. I can check the second with git log on the directory. A low similarity score does not tell me which case happened, so it gives me nothing clear to fix.

The uniqueness assertion

The tree file starts with this rule block. The live system uses Chinese, so I translated it here: 

ASSERT: every durable datum must have exactly one canonical owner.

Classification rules:
1. Classify by the SUBJECT of the information, not by which
   workflow happens to use it.
2. User-specific facts and state never go into modules; modules
   hold only reusable procedure and general knowledge.
3. The first matching branch of the decision tree is the only
   destination. Storing a copy in two places is forbidden.
4. Any other location may hold only:
   - a pointer naming the canonical path, or
   - a derived projection, marked as rebuildable from the source.
5. Moving information requires updating every reference and
   deleting the old copy.

Rule 1 does most of the work. A simple system often files information by use. For example, the travel workflow needs my passport scan, so it saves the scan in the travel module. Later, the immigration workflow needs the same scan and saves another copy. Six months later, one copy may show an old passport. Filing by subject avoids this problem. A passport is an identity document, no matter which workflow needs it. Every workflow then reaches the same copy.

Rule 3 makes the tree a function, not a list of suggestions. The first matching branch wins. The order of the branches therefore changes the result.

Walking the tree, and why the hops are in that order

The live tree asks eight questions in this order:

  1. Does the item contain a credential? Password, token, API key, membership number, or login email. This question comes first because credentials have the strictest storage rule. They leave the normal file tree and go to a separate credential store. No later branch can save a secret by mistake.
  2. Is the item part of an existing project? This question comes second because a project gives a strong ownership signal. It has its own directory, handoff document, and lifecycle. The branch includes this exact rule: “It happened because of this project” is not the same as “it is a project file.” Only the project’s own artifacts and state belong here; cross-project personal state — travel, finance, health, identity — still goes to its own canonical owner. Without this rule, the system would save every fact under the task that happened to produce it. That would still be filing by workflow.
  3. Is it personal information that should last? If yes, it goes into the personal record under its subject area. Most personal facts follow this branch.
  4. Does the document belong to another person? The relationship decides the location, not the file type. Another person's CV belongs with that person or the related project.
  5. Is it reusable reference material with no personal facts? If yes, save it inside a module. This question enforces rule 2. It keeps personal facts out of reusable modules.
  6. Can the procedure be reused? If yes, it is a new module instead of a note.
  7. Is the item part of the system configuration?
  8. No branch matches. Put temporary material in a downloads directory. For anything else, the system stops: if uncertain, you must ask. Do not decide alone. If the user is unavailable, do not store it — wait.

Miss semantics

The eighth branch is important because it allows the tree to stop. The tree does not cover every case on purpose. If no branch fits, the system does not choose the closest one. It asks a person.

Top-k retrieval always returns something. This tree can say, “I do not know where this belongs.” That answer prevents the system from saving facts in the wrong place. Asking one question has a small cost. A fact in the wrong place is much harder to find because the error stays hidden until I need the fact.

One fact, two owners

Some facts are useful in two subject areas. An apartment floor plan matters for both housing and furniture shopping. Rule 4 keeps one copy and adds pointers from the other locations. The tree chooses the one storage path, and cross-links connect the other branches. These are real entries from the anti-duplication table:

Fact Single location How everything else refers to it
CV record/career/ immigration project keeps a pointer file, not a copy
Degree certificates record/education/ same pointer file
Furniture inventory record/living/furniture/ the resale module stores listing status only, and points back
Trip itinerary, PNR, seats record/travel/trips/<date>-<slug>/ calendar entry is a projection, not a second source
Card and account numbers encrypted file under record/finance/ everywhere else holds a pointer; security codes are never written

Databases call this problem an update anomaly. When a fact has two copies, an update may change only one of them. The other copy becomes wrong, and the system may not report the conflict. Database normalization avoids this by storing the fact once and using a key to refer to it. This system uses file paths as those keys.

Ownership and storage are different. Several workflows may own a fact, but the fact must have one copy. Two workflows can both keep the fact current. They still update the same file.

What the rules prevent

Every rule in the assignment file names a location. The ones that hold up also name the failure they exist to stop. Five entries, with the failure written out:

Rule What it prevents
The per-session scratch directory is not storage. Once a scratch file becomes evidence, such as a receipt, a filing confirmation, or a compliance snapshot, it is copied to the owning project and a pointer is written into that project’s status file. Evidence that exists only inside a session that has ended. Nothing later knows to look there.
Identity scans live in one directory. The border-crossing record is excluded by name and fetched from the government site each time it is needed. Filling in a form from a copy that was correct at the last entry. A stored copy gives no sign that it has expired.
One person, one folder. The lookup table at the top of the domain is read before a new name is written down. The same colleague ending up with two folders under two spellings. After that every write picks one of them, and neither is complete.
Reusable knowledge goes in a module. What I personally did goes in the record. Technique comparisons in one place; which provider I used and what I paid in another. A module filling up with personal state, which is what makes it impossible to hand to anyone.
A calendar entry for a trip is a projection of the trip folder, never a second source. Two answers to “what time is the flight” and no rule for which one wins.

Four of the five say what not to store, or where not to put a second copy. Deciding what stays out of the tree turned out to be most of the work.

Where code runs

There is a second address space with the same problem. Not where a file lives, but which machine a job runs on. A separate module owns that decision, and its rules are written the same way: 

Training, evaluation, inference, benchmarking, and smoke tests do not
run on the laptop. Not even one sample.
  → stops an afternoon of an occupied laptop producing a number with no
    job record attached to it.

If the host is unclear, the default is the shared sandbox. Never local.
  → stops the decision being made by whichever machine is in front of me.

Before a remote run, local changes are committed and pushed. The remote
syncs by git pull. Copying source files across is forbidden.
  → stops a result produced by code that exists in no commit. Six weeks
    later there is a number and no way back to what made it.

The run happens in the canonical checkout, at the pushed commit. Not in
a second copy of the repository.
  → stops two checkouts drifting apart while both look current.

Branches are not created or switched unless I asked for that branch by
name. A wrong or dirty branch is reported, not quietly corrected.
  → stops the ground moving under a comparison between two runs.

Before touching a shared machine, an entry goes in the active-work log:
owner, task, checkout path, run directory, commit, outputs, status.
  → stops two people using the same box without knowing it.

Any environment created or changed on any host is written into that
host's environment file in the same step.
  → stops the next run rebuilding an environment that already exists,
    slightly differently.

The last one is the write-back rule from 2.3 appearing early. The step that changes the machine is the step that records the change. Without it the environment file describes the host as it was at some unknown point in the past, which is worse than having no file at all.

What this costs

This design still has a failure mode, but the failure is different:

  • Retrieval may return an irrelevant fact with confidence. It may return a true but unrelated fact. The result does not show whether retrieval found the right item.
  • A directory may return an old fact with confidence. The file may be in the correct location but contain information from three months ago.

I prefer stale data because I can list and inspect it. I can show every file in a domain, sort the files by modification date, and find old entries. An embedding index does not give me a similar list of what it currently believes about my address. But the file tree does not update facts by itself. Even with perfect paths, the system will return old information if nobody saves the new value.

Procedure: assigning an address

  1. Identify the fact's subject, not the task that produced it. If you begin with “this came up while I was...,” you are probably filing by workflow.
  2. Start at question one. Use the first branch that matches, then stop.
  3. If nothing matches, ask the user. Do not invent a location, because the tree will not lead anyone back to it later.
  4. If another workflow needs the fact, add a pointer instead of a copy.
  5. After moving a file, search for the old path. Update every reference, then delete the old copy. Treat these steps as one operation.
  6. Add the new location to the tree file. The tree is the index, so an unlisted location does not exist to the system.

2.2 Domain modules

The address space fixes the fact problem in 1.1. It does not choose which kind of expertise to use. For that, the system has one module for each subject. Every module has the same internal structure. When the system chooses a subject, it loads the full procedure for that subject instead of a few similar text fragments.

The module behind 1.2

There is a module for the question in 1.2: my team is being moved to another organisation, is that good or bad. Its rules are worth reading because they do not tell the model what to say. They take away the answer it would otherwise give. 

R1. Until the reorg analysis is finished, no "good news / bad news"
    conclusion is allowed.

R2. Confirmed fact, first-hand interpretation, rumour, and unknown are
    kept in separate columns.

R2b. Every rumour names its source, and that person's file is opened
     before their credibility is judged. One person is one source. If
     the source has a motive — competing for the same scope, a reason
     to want to be the one telling me — the motive is written into the
     output next to the claim.

R4. Without an official decision, nothing is called a performance plan
    or a targeted removal on fewer than two specific red flags.

R5. If any of {distinct charter, receiving sponsor, assigned resources}
    is unknown, the conclusion is "cannot judge yet". A strong
    destination org, an unchanged reporting line, and an optimistic
    manager do not override this.

R1 and R5 block the reassuring answer. I cannot be told the move is probably fine until three named facts are known. Two of them, who the receiving sponsor is and what resources the new group has been given, are things somebody has to go and find out. R4 blocks the opposite reflex, which is reading a routine change as the start of a removal. Both of those are median answers. They differ only in mood.

R2b came from a specific failure. I had brought a large pile of chat screenshots to a question about an organisational change. The analysis sorted every claim by how well it was verified and never asked what the people making the claims stood to gain. One of them had a personal reason to be the one delivering urgent news to me. Nothing in the procedure asked that question, so the conclusion rested on a motivated source treated as neutral reporting. The fix landed in two places: the rule above, and an earlier gate that opens a person’s file before any analysis that involves them.

The check at the end of the router is two lines:

☐ the conclusion rests on evidence, not on textbook advice
☐ the next step is specific, and does not hand back something I could
  have looked up myself

A general model answers the question it was asked. Asked whether a reorganisation is good news, the median answer is that change brings opportunity and I should talk to my manager. This module cannot produce that answer. What it produces instead is a short list of things I do not yet know, and the order to go and find them out in.

Shape

All 72 modules are directories with the same three parts:

  • SKILL.md contains the router. The front matter contains a description and trigger phrases. The body contains a decision tree and a short list of rules. It tells the system what to load, not how the whole subject works.
  • references/ contains the record for that subject. This directory contains procedures, checklists, and notes from source material. The system reads a file only when the router names it.
  • assets/ contains executable procedures. This directory contains scripts and templates when the module needs them.

The shared structure is not only for neatness. It lets the charter route to any module without knowing the module's contents. If one module uses a different layout, the router needs a special rule for it. The small resident index is then no longer enough.

What is actually resident

The system loads information in stages:

  • On every turn: load the charter (6,960 B) and 72 module descriptions (26,828 B), for 33,788 B total.
  • After a module matches: load the body of its router.
  • When a step needs more detail: load the reference files named by the router.
  • Only when cited: load a specific book chapter.

For one rent negotiation, the negotiation module loaded these files:

SKILL.md                              1,760 B   router
references/framework.md               8,858 B   four-phase tree, always read
references/rent.md                    3,064 B   scenario supplement
references/anti-patterns.md           2,282 B   output gate
                                     ────────
loaded for this request              15,964 B
module on disk                    6,849,002 B
share of the module in context        0.233 %

Three books use almost all of the module's 6.85 MB. The system opens a book chapter only when a step cites it. The same pattern appears across the full system. Routers use 189,028 bytes to index 139,091,825 bytes in 3,080 files, a ratio of about 1 : 736. The index stays small because it does not contain the full content.

A router in full

The full negotiation router is 1,760 bytes. I translated it from Chinese: 

---
name: negotiation
description: "Negotiation assistant: rent, salary, offers, contract
  terms. Decision framework built from Chris Voss + Getting to Yes +
  Influence. Triggers: negotiate, counteroffer, haggle, salary
  negotiation, rent negotiation, renewal, lease negotiation, offer
  negotiation, ..."
---

# Negotiation — decision framework

## Flow

trigger → identify scenario
├─ rent / renewal  → read references/rent.md
├─ salary / offer  → read references/salary.md
└─ anything else   → go straight to the framework

ALL scenarios → read references/framework.md  (four-phase tree)
  Phase 0: PREP     — BATNA + one sheet + market intelligence
  Phase 1: OPEN     — tactical empathy + invite "No"
  Phase 2: EXPLORE  — calibrated questions + interests + black swans
  Phase 3: PROPOSE  — Ackerman + objective criteria + influence
  Phase 4: CLOSE    — three confirmations + get it in writing

after producing text → read references/anti-patterns.md, check line by line
  └─ LOOP until no anti-pattern remains

need depth on a technique? → open the source:
  references/books/never-split-the-difference/   tactical execution
  references/books/getting-to-yes/               principled framing
  references/books/influence/                    psychological levers

## RULES
- The four phases run in order. PREP cannot be skipped.
- Every technique cites its source book; open the chapter for detail.
- The anti-pattern check is the last step, not an optional one.

The router contains no personal facts. Personal information stays in the record, and a step reads it by path only when needed. This is rule 2 from the assertion. It lets someone inspect or share a module without exposing the personal record.

Where the expertise comes from

A module is useful only if it adds something the base model would not produce by itself. I build modules from three kinds of input:

  • Turn books into decisions. A book is parsed, split by chapter, and reduced to useful decisions. The original chapters stay on disk so I can check each claim.
  • Search for current facts. For things no book can provide, such as this month's rent in a building or current salary ranges, the module does not guess. It says where to search and what information to collect.
  • Turn the sources into gates. The output of the first two steps becomes a checklist, not a general summary. The system runs that checklist against its draft.

Gates

The negotiation module has ten gates. Here are four of them, translated from the live system: 

□ 1. Multiple fallbacks
     grep: "alternatively" / "option" / "or we could"
     → Keep exactly one ask. Offering options tells them
       you will accept anything.
     📖 NSTD Ch9: one offer on the table at a time

□ 2. Revealing your floor
     grep: "maximum" / "at most" / "budget"
     → Delete. Your floor is your BATNA. It is an internal tool.
     📖 GTY Ch6: BATNA is not for disclosure

□ 4. Naming competitor prices
     grep: "$" followed by digits
     → Say "competitive offers" instead. A specific number hands
       them an anchor to beat rather than a reason to concede.
     📖 NSTD Ch6: anchoring

□ 6. Length
     body over 150 words → cut
     → Every extra sentence of justification reads as weakness.
     📖 NSTD Ch2: silence is leverage

Each gate follows two rules:

  • Each gate includes exact text to search for. The system does not ask the model whether a draft feels too long or too defensive. It searches for specific text. A check that depends only on model judgment will not run in a consistent way.
  • Each gate includes a source citation. If a gate gives a bad result, I can compare it with the source chapter and change it. I do not need to argue from memory. The citation makes the checklist easier to maintain.

Checklists resist chunking

The gates live together in one file that the router names. A checklist does not work well with similarity retrieval. Suppose you embed ten gates and retrieve the top three for a draft. The system will return the gates most similar to words already in the draft. Those are often the checks the draft already passes. The other seven checks disappear without a warning.

A checklist works only when the system reads every item. Reading three items from a ten-item checklist does not give seventy percent of the value. It silently skips seven checks. The missing checks are often the ones the draft needs most.

Procedure: building a module

  1. Wait until the subject appears for the third time. A single question does not need a module. An unused module still adds text to the resident index.
  2. Write the router first and keep it near 2 KB. Include the scenario branches, the files to read, and the rules that must always run.
  3. Put the full decision process in a reference file, not in the router. A router that explains too much will become too large to load on every turn.
  4. Add an output gate. Run this checklist before showing the draft to the user.
  5. Give every gate a search string and a source citation.
  6. Keep personal facts out of the module. If a step needs one, read it from the record by path.
  7. Register the module so its description enters the resident index. Section 2.3 explains this step.

2.3 Schema evolution

The system changes over time. It gains modules, splits domains, adds gates, changes routes, and removes old parts. Changing the structure is more risky than using it, so structural changes follow stricter rules.

When a change is triggered

Two scheduled events can start a change:

  • Scheduled review. A daily briefing and a weekly review look at recent work and ask what should change.
  • End-of-task check. A check that runs before a task ends asks whether the system should save any lesson from the task. This check catches most problems because the details are still fresh.

What a change can be

  1. Create a module when a subject appears for the third time.
  2. Split a module when it covers two subjects and has two unrelated branches.
  3. Add a gate or rule when a clear failure happens once.
  4. Re-route when facts are going to the wrong owner.
  5. Retire a subject that no longer appears or should not be stored.

If a proposed change does not fit one of these five types, it is not a system change. It is probably a fact, so it should go into the record through the rules in 2.1. This test rejects many vague requests that “the assistant should learn this.”

Who may make it

The registrar controls all five operations. No other module can create, move, or delete system parts. This gatekeeper keeps the structure consistent. Module 72 has the same shape as module 1, so one routing rule can reach both. If every module used a different layout, the router would need a special case for each one. The resident index would no longer contain enough information, and the system would start guessing again.

I created fourteen domains over five months, in four groups. Nine remain today. The first layout did not need to be perfect. It needed a clear rule for change. That rule is what kept five months of changes from becoming a pile of unrelated files.

Five of the fourteen were retired, and each left a rule behind

The retired domains show how the change rules work:

Retired domain What happened What the tree says now
immigration/ outgrew the record, promoted to its own project directory routed at question two, with an explicit note that identity documents stay in the record
ideas/ moved into the career project anti-duplication table names the new canonical path
relationships/ folded into network/ one person, one folder, under network/relationships/

pay_stubs/ deleted, never re-created “do not store — download from payroll when needed”

The last row did not need a better storage location. The system needed a rule to not store the data. The official copy is available through one login, while a local copy can become old without any warning. Border-crossing records and current pay now follow the same rule: fetch them when needed and do not store them. The system stored the border-crossing record once in identity/. That copy became old, so I replaced it with the current rule. The schema must also define what the system should not store. A system that only adds memories cannot express this rule.

Debt is visible

One unfinished split is still on disk. career.md sits next to a career/ directory. Different readings of the tree could send a fact to either location, which breaks rule 3. The same problem exists with identity.md and identity_documents/.

This is not a success. The problem has been open for months. But file paths make the problem visible. ls shows both locations, and a domain audit finds the conflict. An embedding index can contain two documents that disagree. It may mark neither one and choose a different winner for each query. There is no command like ls that lists this conflict. I may discover it only after the system gives a wrong answer.

The write-back rule

The charter includes this rule: 

Never claim something was remembered on the basis of a
store_memory call alone. Conclusions and rules go into a
module or a reference — visible and verifiable.

This rule makes the problem in 1.3 easier to fix. I cannot inspect, compare, or delete a lesson hidden in an opaque memory store. A lesson in a file appears in git log. A person can read it, and I can delete it if it is wrong. Every claim that the system learned something must have a file change behind it.

This article produced one example. An early draft used headings that sounded like marketing. I added a rule to the repository handoff: headings must be noun phrases and cannot be slogans. The next draft must follow that rule. In this system, learning means changing a file that controls future behaviour.

Procedure: changing the system

  1. Describe the failure in one sentence. If you cannot name the failure, do not change the system.
  2. Choose one of the five change types. If none fits, save the information as a fact and stop.
  3. Find the existing module that owns the subject. Add a gate before creating a new module.
  4. Make the change in one place only.
  5. Search for the old path or rule. Update every reference, then delete the old copy.
  6. Add the change to the tree file. If the index does not include it, the system cannot use it.
  7. Write the result you expect. The next review can then check whether the change worked.
What is not measured

I do not measure how often the system chooses a wrong route. To detect a wrong route, I must already know the correct route. Today, I usually find these mistakes while looking for something else. A stronger system would log every assignment and the branch that matched. It would review a sample each week and track facts that have not been updated after the real-world value changed. My system does neither today.

The zero in the last row needs an explanation. Similarity search is useful for finding text about a topic. It is less suitable for finding the current value of a fact. This system mostly answers questions like “what is true right now?” It therefore uses file paths instead of similarity distance. A system for literature search would make a different choice.

The system still needs manual work. A person writes and updates all of this text. Fourteen domains became nine because someone moved the files. Five domains were retired because someone noticed they were no longer correct. The design does not remove maintenance. It makes the maintenance work easy to list and inspect.
