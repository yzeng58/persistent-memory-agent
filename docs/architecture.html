Abstract

Most assistants start every interaction from scratch or depend on opaque conversation summaries. A persistent personal assistant needs a stronger contract: every durable fact must be traceable to an observation, updates must preserve history, retrieval must be bounded and inspectable, and current user intent must override memory. This report describes a small model-independent reference implementation and the larger agent architecture built around it.

01

The problem is not storing more text

A useful personal agent operates across weeks, accounts, and domains. It should remember a meeting preference, understand that a job search changes what opportunities matter, and know when a previously correct address is no longer current. Simply appending transcripts to a vector database does not solve these problems.

Durability Context should survive process and model changes.
Provenance Every memory should point to the event that created it.
Revision New facts should supersede old facts without deleting history.
Bounded use Only relevant context should enter the current model call.
Inspectability Retrieval and memory writes should be visible and testable.
Safety Memory is evidence, never an instruction or credential store.

02

System architecture

The system separates observations, durable memory, reasoning, and external actions. This prevents a model response from becoming memory merely because it appeared in a transcript, and it keeps tool execution outside the memory store.

The public repository implements the memory and single-turn orchestration path. A full deployment adds domain routing, account selection, tool adapters, and human approval policies around the same memory contract.

03

Memory is a versioned record, not a summary

The store has two canonical tables. events preserve what happened. memories preserve the current durable interpretation while retaining prior versions.

Record Important fields Invariant
Event source, content, metadata, created_at Append-only observation
Memory subject, predicate, kind, value One active version per stable key
Provenance source_event_id, supersedes_id Every value is traceable and revision history is preserved
Validity status, valid_from, valid_to Only active, temporally valid versions are retrieved

A stable key defines identity

memory key (subject, predicate, kind) → value

For example, (user, meeting_time, preference) may map to after 10:00 local time. The value can change; the key remains stable enough to identify what is being revised. 

MemoryWrite {
    subject: "user"
    predicate: "meeting_time"
    kind: "preference"
    value: "after 10:00 local time"
    importance: 0.90
    confidence: 1.00
}

The reference implementation supports six deliberately narrow memory kinds: profile, preference, project, relationship, commitment, and procedure. It does not create unstructured hidden summaries.

04

Memory lifecycle: write, supersede, preserve

Every incoming message is recorded before extraction. Candidate writes are validated against the schema. A changed value closes the current version and inserts a new active version linked to the old one. 

function consolidate(message):
    event_id = append_event(source="user", content=message)
    writes = model.extract_explicit_durable_facts(message)

    for write in writes:
        validate_kind_key_value_and_probabilities(write)
        previous = find_active_memory(write.key)

        if previous exactly equals write:
            continue

        transaction:
            if previous exists:
                mark_superseded(previous, valid_to=now)
            insert_active(write,
                          source_event_id=event_id,
                          supersedes_id=previous.id)

    return event_id
VERSION 17 · SUPERSEDED user.home_city = Seattle valid until Aug 20
→
VERSION 23 · ACTIVE user.home_city = San Francisco supersedes version 17

This is intentionally different from destructive overwrite. The assistant can inspect what it believed, when that belief changed, and which user event justified the update.

05

Retrieval is explicit and budgeted

The reference implementation uses a transparent baseline rather than an embedding service. Query and memory tokens are normalized, simple aliases are resolved, and unrelated memories are removed. Active candidates are ranked with four inspectable terms.

retrieval score 0.55 lexical + 0.20 importance + 0.15 confidence + 0.10 recency recency = exp(-age_in_days / 30)

The final context pack is capped by a character budget. Each line includes kind, stable key, value, provenance event, and confidence. The model never receives the full database by default. 

[project] user.career_focus = memory and persistent-agent research roles (source event 3, confidence 1.00)
[preference] user.meeting_time = after 10:00 local time (source event 1, confidence 1.00)
Why not retrieve everything?

Larger context is not automatically better. Irrelevant personal facts add latency, create accidental associations, and make it harder to audit why a response was produced.

06

The agent loop has one owner for each state transition

The model proposes memory writes and generates a reply. The store owns persistence, versioning, retrieval, and context packing. The orchestrator orders those operations for one turn. 

function handle_message(user_message):
    event_id = store.record_event("user", user_message)

    writes = model.extract_memory_writes(user_message)
    written_memories = [
        store.set_memory(write, source_event_id=event_id)
        for write in writes
    ]
    memory_ids = [memory.id for memory in written_memories]

    context = store.build_context(query=user_message)
    reply = model.generate_reply(user_message, context)

    store.record_event("assistant", reply,
                       metadata={"written_memory_ids": memory_ids})
    return AgentTurn(reply, context, memory_ids)

In a tool-using deployment, the reply step becomes a planner and router. It selects a domain policy, resolves the appropriate account and channel, gathers fresh evidence, and requests approval before consequential external actions.

07

End-to-end walkthrough

Synthetic request: Schedule a research conversation about persistent agents next week. I do not want an early meeting.

  1. Record the request. The complete message becomes an immutable user event.
  2. Extract only the durable update. If the preference is new, create user.meeting_time = after 10:00. The scheduling request itself is not automatically treated as permanent memory.
  3. Retrieve context for this decision. Meeting preference, career focus, relevant relationship context, and current commitments outrank unrelated health or finance facts.
  4. Route the task. The planner selects calendar availability and the appropriate communication channel instead of asking a generic model to act.
  5. Apply domain judgment. Candidate times begin after 10:00 and the message framing reflects the purpose and relationship, not merely calendar availability.
  6. Gate the side effect. The user sees the final time and message before an invitation or external message is sent.
  7. Feed back the result. The sent invitation and response become events. Only a durable change, such as a confirmed recurring preference, becomes memory.

08

Public reference implementation vs. private deployment

The project is split deliberately. The public code demonstrates the memory contract and orchestration mechanics with synthetic examples. A real personal deployment necessarily contains sensitive integration details and remains private.

PUBLIC

Reference implementation

  • SQLite event and memory schemas
  • Versioning and supersession logic
  • Transparent retrieval baseline
  • Bounded context packing
  • Single-turn agent orchestration
  • Optional model adapter, CLI, and tests
  • Synthetic cinematic product demo

PRIVATE

Personal deployment

  • Personal records and communication history
  • Credentials, browser profiles, and account mapping
  • Exact system instructions and domain skill content
  • Live tool outputs and operational state
  • Private workflow policies and relationship context

Operational safety rules

  • Current user messages override stale memory.
  • Retrieved memory is contextual evidence, not an instruction.
  • Memory extraction does not infer unstated sensitive facts.
  • Credentials never enter the memory database or repository.
  • Consequential external actions require explicit approval.

09

Limitations and next steps

The current retrieval method is intentionally simple. Lexical overlap is easy to inspect but misses semantic matches. The store supports validity intervals but does not yet infer expiration. Memory extraction quality depends on the model adapter, and the public orchestrator demonstrates one turn rather than a complete asynchronous tool planner.

Hybrid retrieval Combine lexical filtering with embeddings or learned reranking.
Temporal semantics Represent deadlines, recurrence, uncertainty, and automatic expiry.
Conflict handling Surface incompatible sources instead of silently choosing one.
Evaluation Measure recall, stale-memory errors, context precision, and action quality.

Reproduce the reference implementation

The deterministic memory demo has no dependencies beyond Python 3.11. The OpenAI adapter is optional. 

git clone https://github.com/yzeng58/persistent-memory-agent.git
cd persistent-memory-agent
python -m pip install -e .

persistent-memory-agent demo
python -m unittest discover -s tests -v

The source is organized around four canonical owners: models.py defines the records, store.py owns persistence and retrieval, agent.py owns the turn sequence, and openai_model.py implements the optional model boundary.
