01

One fact, one address

An assistant that has known you for six months fails in a very specific way. It does not forget. It surfaces something true, from some earlier conversation, that has nothing to do with what you are doing right now — and then it quietly steers the answer with it.

That is not a recall problem. It is an addressing problem. The whole system rests on two invariants:

Exactly one place Every durable fact lives in exactly one writable file. Not one per workflow. One, total.
A computable address Given the fact, you can derive the path that holds it without searching for it.

Similarity search over stored conversation cannot give you either one, and the reasons are structural rather than a matter of tuning:

  • A vector store has no primary key. There is no UPDATE. A corrected fact is appended as a second, competing fact, and cosine distance decides which one wins at read time.
  • top-k always returns k. It has no way to say nothing here is relevant. It will always hand you five things, whether or not five things exist.
  • Similar is not the same as binding. She locked this position and she likes this stock sit close together in embedding space. One is a hard constraint, the other a preference. Similarity has no dimension for the difference.
  • A corpus is not a state store. A corpus can tell you everything ever said about your address. It has no representation of your address right now.
The distinction the whole design rests on Retrieval is a guess. Routing is a decision.

Both designs fail. What matters is that they fail differently, and that one of the two failures is one you can actually see:

SIMILARITY SEARCH Confidently irrelevant The memory is accurate and was retrieved for the wrong moment. Nothing in the output tells you this happened.
vs
ADDRESSED FILES Confidently stale The lookup was correct and the file was never updated. The file has a path and a timestamp, so the failure has a location you can go inspect.

One more distinction, because it is where most people get the rule wrong. Plenty of facts belong to two subjects at once — the card you pay the mortgage with belongs to both the house and to your finances. The temptation is to write it down in both places. Do that and you have manufactured the oldest bug in data modelling: you will update one copy, miss the other, and the two will disagree forever. Relational design has a name for it, the update anomaly, and a fix that is now fifty years old — store the fact once, and point at it from everywhere else.

Owners may be many. Copies must be one.

A file can be reached from several places in the tree. That is a feature. What must never happen is the same fact existing as two independently editable copies.

02

The shape uniqueness forces

If every fact must have an address you can compute rather than search for, then something has to compute it. That something is a decision tree, and it is the first file the system loads. This is the top of the real one: 

ANY TASK
├─ a skill matches               → invoke that skill, do not improvise
├─ a person is mentioned         → people-ops        → network/<person>/
├─ a project is named            → projects.md       → path, URL, status
├─ scheduling                    → calendar-ops
├─ mail                          → email-ops
├─ a web page must be opened     → browser
├─ an experiment must run        → experiment-ops + env-control
├─ code is written or debugged   → code-writing
├─ identity / legal / contract   → high-stakes       → read literally, zero loss
├─ a file is created or sought   → system-maintenance → file-directory.md
└─ the system itself changes     → system-maintenance → registrar gate

The rule that governs the whole structure is one line, and it is the single most useful sentence in the system:

from file-directory.md Walk this tree before you write a file.
Walk the same tree when you look for one.

This is what similarity search structurally cannot do. There, writing is embed and insert and reading is embed the query and take the top k — two different functions, which is exactly why reading can only ever approximate what writing did. Here it is one function used in both directions, so a lookup is exact rather than close.

The spine is a tree; the cross-links make it a graph

A strict tree breaks the moment a fact has two legitimate parents. The resolution is not to duplicate and not to agonize over which parent is truer — it is to let both branches terminate at the same file. Many entry points, one copy. My own system does this to itself: two of its skill names are pure aliases that resolve to canonical modules elsewhere, kept alive so that older instructions referencing the old name still land in the right place. 

finance-ops    → alias → asset-snapshot
facebook-ops   → alias → secondhand-ops

Every domain module has the same three parts

Health, money, travel, appearance: each is its own small system with its own procedures. What makes seventy of them navigable is that all seventy have identical anatomy.

1
Router — SKILL.md

A decision tree plus hard rules. Must stay small enough that loading it is never a decision. Mine average 2.6 KB.

2
Procedures — assets/

Executable steps, scripts, templates. Read only when the router sends you there.

3
The record — references/

Durable facts and distilled knowledge. Can be arbitrarily large, because it is never loaded speculatively.

That split is what keeps the context window from being the binding constraint. The routers are a constant; the knowledge behind them is a variable.

03

What is worth saving

Everything above is about the read side, and the read side is the easy half. These systems actually die on the write side — either because nothing gets written down, or because everything does and the tree fills with noise that outranks the facts.

A fact earns its own file only when all three hold:

  • It outlives the conversation. If it stops mattering when the task ends, it is scratch, not memory.
  • It has exactly one subject. If you cannot name the subject, you cannot compute the address, and it will end up somewhere arbitrary.
  • Someone could check it. Prefer the account number, the date, the confirmation code. Impressions age badly and cannot be verified later.

Four things that should never become durable memory:

  • Reasoning you could redo from the facts you already stored.
  • Anything derivable — store the vest schedule, not the monthly total.
  • Raw transcripts. A transcript is evidence, not state.
  • Session scratch. My charter says it explicitly: session state is not long-term storage. Work in progress that is never promoted is simply lost, on purpose.

The part that took me longest to get right: the decision to save should not be discretionary. It should be routed by the same tree that decides where. The charter does not say remember important things about people. It says:

write-side routing A person is mentioned, even in passing → people-ops → network/

Same trigger, same destination, every session, regardless of which model is running. That is what makes the address predictable a year later.

04

The control plane

Each domain is a small system with its own construction and its own operating rules. Nothing stops seventy of them from drifting into seventy different conventions except a layer that does no domain work at all. The vocabulary from network and cluster design fits exactly, so I use it:

DATA PLANE

Domain modules

  • Seventy modules: money, health, travel, writing, compute, people.
  • Each owns its own record exclusively.
  • Reaches another domain by pointer, never by copying its facts.
  • This is where all actual work happens.

CONTROL PLANE

Charter and registrar

  • Does no domain work whatsoever.
  • Owns the top-level route and the invariants.
  • Is the only thing allowed to create, merge, move, or delete a part.
  • Enforces that every module has the same anatomy.

It has two components, and they have different jobs:

C
The charter — always resident

About four kilobytes, loaded every session before anything else. Holds the top-level route, the non-negotiables, and the rule that a matching module must be invoked rather than improvised from memory.

R
The registrar — invoked on change

Decides where a new file goes, how a module is created or split, what documentation style applies, and runs the pre-completion audit. It is the only writer permitted inside the system directory.

The registrar guards itself with an assertion, because a system that can edit its own rules without friction will eventually edit away the rule that was protecting you:

Registrar gate

  • No write to the system directory until the exact file, scope, and text are approved in this same task.
  • Otherwise: present the proposal and stop.
  • After any change: verify line counts and inbound references, then emit a change report.
  • Delete the old entry point. Leaving a working legacy path invites future sessions to use it.
The registrar’s product is not skills. It is sameness.

Uniform anatomy is the entire reason one small router can navigate seventy subsystems. The moment modules are allowed to each have their own shape, the top-level tree stops being able to address them and you are back to searching.

05

How to build one

Everything above condenses into eight steps. They are ordered; the first two are the ones that are expensive to change later.

  1. Write the router before the content. If you cannot write the decision tree that finds a fact, you do not yet know where that fact belongs. Content written before its router always has to be moved.
  2. Classify by subject, not by workflow. A fact is used by many workflows but is about exactly one subject. Filing by workflow guarantees duplication; filing by subject makes uniqueness automatic. This is the single highest-leverage decision in the whole design.
  3. Make the address computable. From the fact alone you should be able to derive the path. If finding it requires a search, the classification rule is not yet sharp enough.
  4. Reference, never replicate. When two domains need the same fact, the second one gets a pointer. Two copies are two futures in which one of them is wrong.
  5. Keep routers a constant, put the mass in leaves. Anything that grows without bound belongs behind the router, never inside it. A router that grows with your knowledge stops being loadable exactly when the knowledge gets good.
  6. Route the write, not just the read. Attach saving to triggers in the charter. A rule that depends on the model deciding to be diligent is not a rule.
  7. Put a gate on the output. Generation is not the last step. A checklist that can reject the draft and send it back is what separates a good answer from a good-enough one. Section seven is entirely about this.
  8. Let the schema grow. Do not design it. Ten domains chosen up front will be wrong, and wrong up-front schemas are the expensive kind. Split a folder when it stops being uniquely addressable, and not before.

That last one is not advice I reasoned my way to. It is just what the commit history shows. I never sat down and designed a taxonomy of my own life; domains split off, one at a time, each time a folder had accumulated enough that its contents stopped having one obvious home.

07

Turning books into gates

Everything so far is plumbing: it makes the system know you. It does not make the system any good at the things you are bad at. And the moments where an assistant is genuinely worth having are exactly those — managing up, negotiating a lease, reading a room you are too close to.

Ask a general chatbot about any of them and you get an answer from the middle of the distribution, because that is what it was trained near. Median advice on a negotiation is not merely unhelpful; it is the advice your counterparty is expecting.

the problem this section solves You do not want the median answer.
You want a specific expert’s answer, with the citation attached.

Three moves, in order.

a. Distill the book

  • Books are ingested by a module, not dropped in a folder. The pipeline parses the source, splits it into chapters, writes an index, then adds pointers from the places that should trigger it.
  • Its filing rule is the uniqueness rule applied to knowledge: a book lives with the module that uses it, never in a global library. There is no books/ at the root.
  • A distilled book is an index.md (one paragraph of thesis, roughly a dozen named concepts, a chapter table with one line each) beside chapters/ and the original file, which is deliberately kept. Distillation builds an index over the source; it does not replace it. You can always re-distill. Chunked embeddings are a one-way door.
  • Pick books that occupy different layers rather than three that agree. The negotiation module carries exactly three: one for tactics, one for principled framing, one for the psychology of influence.

b. Search for what changes

  • Books give you the invariants. They cannot give you this month’s vacancy rate. So each scenario file separates the two explicitly and lists the facts that must be looked up fresh every time — comparable rents, vacancy rate, concessions being offered nearby, the current inflation print, the landlord’s turnover cost.
  • Each one is stored with its source and with how it is used, not just what it is. A vacancy rate above five percent is not a statistic; it is the reason you have leverage.

c. Compile it into a gate

This is the part that actually produces the quality difference, and the part almost nobody builds. Generating the draft is not the last step. The draft is then checked against a list that can reject it. 

write the draft
   ↓
run every check
   ↓
any failure → revise → run every check again
   ↓
all pass → only now may it be sent

Five of the ten checks, as they are actually written:

CheckMechanicallySource
No menu of options Search for alternatively, we could, or. Keep one ask. Offering options tells them you will take anything. Never Split the Difference, ch. 9
Never state your ceiling Search for at most, budget, maximum. Your walk-away is an internal instrument. Getting to Yes, ch. 6
No competitor numbers Search for currency figures. Say competitive offers. A specific number is a target to beat by one dollar. Never Split the Difference, ch. 6
Length ceiling Over 150 words, cut. Every extra sentence of justification reads as doubt. Never Split the Difference, ch. 2
Never a round number $2,200 becomes $2,173. A precise figure says you calculated. A round one says you guessed. Never Split the Difference, ch. 9

The last one is the cheapest demonstration of the whole idea. Ask any general assistant to write a rent negotiation email and it will propose a round number, because round numbers are what the median writer uses. Mine cannot: check eight rejects the draft, and it can tell you the rejection came from chapter nine of a specific book that is sitting on the disk next to the rule.

Distillation’s output is not a summary. It is a checklist with citations.

A summary is unusable at the moment of writing. A gate is usable precisely then. That is the whole difference between having read a book and having the book in the loop.

08

What it costs

This design pays for its precision, and mostly in places you do not notice until months in.

The cost moves to write time Every fact must be classified when it arrives. Similarity search defers that work to read time. Deferring is cheaper per event and worse per year.
Confidently stale If nothing writes, the tree returns last month’s answer with total confidence. Similarity search would have surfaced the recent conversation. This is a real inversion, not a rhetorical one.
Migration debt is visible Two of my domains still have both a flat file and a directory with the same name — a split that started and never finished. Growing the schema means periodically paying to finish moves.
No promotion between domains A claim recorded in one domain does not automatically upgrade a fact in another when it turns out to be true. There is no edge for that yet, and it has to be walked by hand.
Cold start is real A router with nothing behind it is worse than no system. The payoff arrives only after a domain has enough record to be worth routing to.
None of this is benchmarked These are field notes from one system used daily for six months, not an evaluation. The measurements I would want: stale-fact rate, misroute rate, and how much of what enters context was actually load-bearing.

The honest summary is that I traded a failure mode I could not see for one I can. A wrong file has a path and a modification date. A retrieval that quietly pulled the wrong memory into context leaves nothing behind at all.

09

Reproduce

The deterministic memory substrate is public and has no dependencies beyond Python 3.11. The model adapter is optional. 

git clone https://github.com/yzeng58/persistent-memory-agent.git
cd persistent-memory-agent
python -m pip install -e .

persistent-memory-agent demo
python -m unittest discover -s tests -v

The source keeps one canonical owner per concern, which is the same rule the file tree uses: models.py defines the records, store.py owns persistence and retrieval, agent.py owns the turn sequence, and openai_model.py implements the optional model boundary.

If you build one of these, the two decisions that are expensive to reverse are both in section five: write the router before the content, and classify by subject rather than by workflow. Everything else can be refactored later.
